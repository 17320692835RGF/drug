## 1. 项目概述

RDC（Radionuclide Drug Conjugate，放射性核素药物偶联物）数据查询平台，是一个面向医药研发/科研人员的 B/S 架构数据服务系统。

### 1.1 核心能力

- **RDC 药物查询**：药物列表（分页/筛选/排序）、模糊搜索、按状态筛选、详情查询
- **化学实体查询**：五类化学实体（冷化合物 Cold Compound、配体 Ligand、连接子 Linker、螯合剂 Chelator、放射性核素 Radionuclide）的详情、搜索、关联 RDC 列表
- **关联数据查询**：药物 ↔ 靶点、适应症、化学实体、文献的关联关系；体内外实验数据（人体活性、动物体内研究、体外研究）
- **访问统计**：全站访问埋点、IP 地理位置解析、管理后台统计看板（含地图分布）
- **数据维护**：CSV 数据校验 → MySQL 差异比对的入库流程，支持 GitHub Actions 手动触发

### 1.2 系统特点

- 前后端同构：页面与 API 同属一个 Next.js 应用，单进程部署
- 数据驱动：所有业务数据存于 MySQL，静态图片资源走 CDN
- 可重复数据更新：CSV 为数据源，校验脚本 + upsert 脚本保证幂等写入

```text
                          ┌─────────────────────────────┐

                                         │ HTTPS
                          ┌──────────────▼──────────────┐

                                         │ http://127.0.0.1:3101
                    ┌────────────────────▼────────────────────┐
                    │      Next.js 14 应用（PM2 守护）          │
                    │  ┌───────────────┐  ┌────────────────┐  │
                    │  │ 页面渲染 (SSR) │  │ API Routes     │  │
                    │  │ app/*/page.tsx│  │ app/api/*      │  │
                    │  └───────────────┘  └───────┬────────┘  │
                    │            ┌────────────────┘           │
                    │            ▼                            │
                    │   lib/rdc-data.ts（数据访问层）           │
                    │   lib/db.ts（MySQL 连接池）               │
                    └────────────┬────────────────────────────┘
                                 │ mysql2
                    ┌────────────▼────────────┐
                    │      MySQL (rdcdb)      │
                    │      17 张业务表         │
                    └─────────────────────────┘

    外部依赖：
    - IP 地理位置查询服务（app/api/visit 使用，3s 超时）
    - CDN（NEXT_PUBLIC_ASSET_BASE）：分子结构图等静态资源
```

### 2.1 请求处理流程

1. Nginx 将 443 流量转发至本机 3101 端口（PM2 托管的 `next start`）
2. 页面请求由 App Router 服务端渲染；数据请求由客户端组件调用 `/api/*`
3. API 层做参数校验（`lib/query.ts`）→ 调用数据访问层（`lib/rdc-data.ts`）→ 返回 JSON
4. 出错时返回统一错误结构（`lib/http.ts`）

## 5. 数据库设计

数据库名 `rdcdb`，字符集 `utf8mb4_unicode_ci`，引擎 InnoDB。建表脚本见 `main.sql`，共 17 张业务表 + 1 张运行时表（`site_visits`）。

### 5.1 ER 关系总览

```text
rdc_drug（药物主表）
 ├── drug_target ──── target（靶点）
 ├── drug_indication ─ indication（适应症）
 ├── drug_chemical_rel ─── chemical_entity（化学实体，五类合一）
 │                            └── chemical_affinity（亲和力）
 ├── in_vitro ──── in_vitro_measurement（体外测量明细）
 ├── human_activity（人体活性/临床数据）
 ├── animal_in_vivo_study（动物体内研究头表）
 │     ├── animal_in_vivo_biodist（生物分布明细）
 │     └── animal_in_vivo_efficacy（疗效明细）
 └── rdc_drug_reference ─── reference（文献）
site_visits（站点访问记录，运行时表，不在 main.sql 中）
```

### 5.2 表清单

| 表名 | 业务编号字段 | 说明 |
| --- | --- | --- |
| `rdc_drug` | `drug_id`（唯一） | 药物主表：名称、别名、状态、类型（Treatment/Diagnosis）、SMILES、结构图、ChEBI/PubChem 编号、放射化学指标 |
| `target` | `target_id`（唯一） | 靶点主表，`(name, external_id)` 唯一 |
| `drug_target` | 联合键 `(drug_id, target_id)` | 药物-靶点多对多，含 evidence 证据字段 |
| `indication` | `indication_id`（唯一） | 适应症主表，含 ICD-11 编码 |
| `drug_indication` | 联合键 `(drug_id, indication_id)` | 药物-适应症多对多 |
| `chemical_entity` | `entity_category` + `entity_id`（联合唯一，`entity_id` 全局唯一） | 五类化学实体合并存储：`ENUM('cold_compound','ligand','linker','chelator','radionuclide')`；含分子描述符（MW/LogP/TPSA/HBD/HBA/可旋转键等）、核素专用字段（符号/半衰期/辐射类型/能量） |
| `drug_chemical_rel` | 联合键 `(drug_id, relation_role, chemical_entity_id)` | 药物-化学实体多对多，`relation_role` 为实体类别 |
| `chemical_affinity` | `affinity_id`（唯一） | 实体亲和力：类型（Kd/Ki/IC50）、符号、数值、单位、来源 |
| `in_vitro` | `in_vitro_id`（唯一） | 体外研究头表（概览、PMID/DOI） |
| `in_vitro_measurement` | 无业务键（`in_vitro_ref_id` 外键） | 体外测量明细：类别（partition_coefficient/affinity/other…）、类型（logP/IC50…）、符号/数值/单位 |
| `human_activity` | `activity_id`（唯一） | 人体活性/临床数据：试验登记号、适应症、受试者、剂量、终点、疗效、不良事件 |
| `animal_in_vivo_study` | `study_id`（唯一） | 动物体内研究头表 |
| `animal_in_vivo_biodist` | `study_ref_id` 外键 | 生物分布明细：剂量、检测时间、代谢/排泄、7 项肿瘤/器官 TBR 比值 |
| `animal_in_vivo_efficacy` | `study_ref_id` 外键 | 疗效明细：模型、剂量、疗效描述、不良反应 |
| `reference` | `reference_id`（唯一） | 文献主表：标题、作者、期刊、DOI/PMID、摘要 |
| `rdc_drug_reference` | 联合键 `(drug_id, reference_id)` | 药物-文献多对多 |
| `site_visits` | 自增 id | 访问记录：ip、country/country_code/region/city、latitude/longitude、user_agent、path、visited_at（**该表由代码维护，未纳入 main.sql**） |

### 5.3 设计要点

- **主键策略**：所有表使用自增 `id` 作物理主键，业务编号（`drug_id` 等）加唯一索引作逻辑主键，关联表外键均指向业务编号字段
- **级联删除**：所有关联表 `ON DELETE CASCADE ON UPDATE CASCADE`，删除药物时自动清理关联数据
- **软删除**：无，数据修正通过 CSV 补丁流程完成，apply 前自动建备份表
- **注释掉的表**：`animal_in_vivo_pk`（药代动力学明细）在 main.sql 中被注释，暂未启用，但 API 响应结构中保留了 `pk` 字段位
- **外键缺口**：`drug_chemical_rel` 对 `chemical_entity` 的复合外键被注释（见 main.sql L175），依赖应用层保证一致性

## 6. API 接口文档

### 6.1 通用约定

- **Base URL**：`https://rdcdb.com/api`（本地 `http://localhost:3101/api`）
- **请求方式**：全部为 `GET`，除 `/api/visit` 为 `POST`
- **成功响应**：直接返回数据 JSON（无统一包裹层）
- **错误响应**（统一结构，见 `lib/http.ts`）：

```json
{
  "error": {
    "code": "VALIDATION_ERROR | NOT_FOUND | SERVER_ERROR",
    "message": "错误描述",
    "details": ["出错的参数名"]
  }
}
```

| HTTP 状态码 | code | 场景 |
| --- | --- | --- |
| 404 | NOT_FOUND | 资源不存在 |
| 422 | VALIDATION_ERROR | 参数缺失/非法 |
| 500 | SERVER_ERROR | 服务端异常 |

- **分页参数**：`page`（默认 1，最小 1）、`page_size`（默认 20，范围 1–100）
- **expand 参数**：逗号分隔，支持 `chemicals`、`human_activity`、`animal_in_vivo`、`in_vitro`；`all_entities=true` 等价于全展开
- **布尔参数**：`true/1/yes/y` 为真，`false/0/no/n` 为假（`lib/query.ts`）

### 6.2 RDC 药物接口

#### `GET /api/rdc/init`

初始化状态枚举字典。

```json
{ "dicts": { "status": [ { "value": "Approved", "label": "Approved" }, ... ] } }
```

实现：`SELECT DISTINCT status FROM rdc_drug`（`listStatusDict`）。

#### `GET /api/rdc`

药物列表，支持分页、过滤、排序。

| 参数 | 类型 | 说明 |
| --- | --- | --- |
| `page` / `page_size` | int | 分页 |
| `q` | string | 药物名模糊匹配 |
| `status` | string | 按状态精确过滤 |
| `sort` | string | 枚举：`created_at:desc`（默认）/ `created_at:asc` / `drug_name:asc` / `drug_name:desc`，白名单校验 |

响应：`{ items, page, page_size, total }`，每条 item 含五类化学实体的主选名称（`cold_compound_name` / `ligand_name` / `linker_name` / `chelator_name` / `radionuclide_name`）。

#### `GET /api/rdc/search?q={关键词}&limit={n}`

药物名模糊搜索，`q` 必填，`limit` 默认 20（1–100）。返回 `{ items: [{drug_id, drug_name, status}] }`。

#### `GET /api/rdc/by-status?status={状态}&limit={n}`

按状态筛选药物，`limit` 默认 50（1–200）。

#### `GET /api/rdc/detail?drug_name={名称}`

按药物名精确查询（大小写不敏感）基础信息（不含关联数据）。

#### `GET /api/rdc/{drug_id}?expand=&all_entities=`

药物详情。基础返回 `general` 块（主表全字段）+ `chemicals` 块（五类实体主选名称）；`expand` 控制附加块，`all_entities=true` 时 `chemicals.entities` 返回按类别分组的全部关联实体。

各展开块结构：

- `human_activity`：临床试验数组（登记号、适应症、患者、剂量、终点、疗效、不良事件等）
- `animal_in_vivo`：`{ studies: [{ study_id, pmid, doi, pk: [...], biodistribution: [...], efficacy: [...] }] }`
- `in_vitro`：`{ studies: [概览], <measurement_category>: [测量明细...] }`（按测量类别动态展开为键）

> 实现细节：即使未请求某些 expand 段，响应中也会以空值占位（`human_activity=[]`、`animal_in_vivo={studies:[]}`、`in_vitro={}`），保证前端结构稳定（见 route L39-47）。

### 6.3 化学实体接口

实体类别 `entity_category` 合法值：`cold_compound` / `ligand` / `linker` / `chelator` / `radionuclide`。

#### `GET /api/chemical/{entity_category}/{entity_id}?include_activity=`

实体详情。`include_activity` 默认 `true`：
- `basic`：实体全字段（名称、别名、SMILES、分子式、InChI、PubChem CID、分子描述符、类别专用字段等）
- `rdc_activity`：关联 RDC 药物及其活性数据聚合（含 `human_activity`、`animal_in_vivo`、`in_vitro`）

`include_activity=false` 仅返回 `basic`。

#### `GET /api/chemical/{entity_category}/{entity_id}/rdc-list`

查询该实体关联的 RDC 药物列表（轻量版，不含活性数据）。

#### `GET /api/chemical/search?entity_category={类别}&q={关键词}&limit={n}`

在指定类别内按名称搜索实体，`q` 必填。

### 6.4 靶点接口

#### `GET /api/target/{target_id}`

靶点详情 + 关联药物列表（含每个药物的配体名称子查询）。此路由**直接在 route 中写 SQL**（不走 rdc-data 层）。

### 6.5 文献接口

#### `GET /api/reference/{drug_id}`

查询药物关联文献，按发表日期倒序：

```sql
SELECT r.*, dr.note AS relation_note
FROM rdc_drug_reference dr
JOIN reference r ON r.reference_id = dr.reference_id
WHERE dr.drug_id = ?
ORDER BY r.publication_date IS NULL, r.publication_date DESC, r.title ASC
```

响应：`{ drug_id, references: ReferenceItem[] }`。

### 6.6 访问统计接口

#### `POST /api/visit`

访问埋点。由全局组件 `VisitTracker` 在路由变化时自动调用，body：`{ path }`。

处理逻辑（`app/api/visit/route.ts`）：
1. 从 `x-forwarded-for` / `x-real-ip` / `req.ip` 提取客户端 IP
2. 内网 IP（127.x、192.168.x、10.x、172.16-31.x）标记为 `Local`
3. 外网 IP 调用第三方地理位置服务（3 秒超时 AbortController），获取国家/城市/经纬度
4. 优先复用同 IP 已有归属地记录，未命中才请求外部服务
5. 写入 `site_visits` 表

#### `GET /api/visit-stats`

管理端统计（供 `/admin/visits` 看板使用）：总量、独立 IP 数、首次访问时间、按国家聚合（Top 100）、最近 20 条记录、地图打点数据。`export const dynamic = "force-dynamic"` 禁用缓存。

#### `GET /api/visit-public`

公开统计（供首页展示）：仅返回 `{ total, firstVisit }`，响应头强制 `no-store` 防缓存。

## 8. 核心模块实现说明

### 8.1 数据访问层 `lib/rdc-data.ts`

API 层唯一的数据入口（MySQL 实现），主要职责：

- **列表/搜索**：动态拼装 WHERE/ORDER BY，`normalizeSort` 仅允许 4 种排序组合（防注入），limit 全部钳制在安全区间
- **详情聚合**：`getDrugDetail` 按 expand 参数并行组装 general/chemicals/human_activity/animal_in_vivo/in_vitro 五大块；体内研究按 study → pk/biodist/efficacy 三级嵌套
- **实体详情**：`getChemicalDetail` 支持附带 `rdc_activity`（递归调用 `getDrugDetail` 全展开聚合）
- **容错**：`isMissingTableError` 捕获 `ER_NO_SUCH_TABLE`，表不存在时返回空数据而非 500（保证首次部署未导数时页面可用）
- **字段映射**：数据库 snake_case → API camelCase 部分转换，日期统一 `toISOString()`

### 8.2 数据库连接 `lib/db.ts`

mysql2 连接池单例：

```ts
{ host, port, user, password, database, waitForConnections: true,
  connectionLimit: 10, namedPlaceholders: true }
```

通过 `getPool()` 惰性初始化，`withConnection(fn)` 包装执行。配置全部来自环境变量，带默认值（127.0.0.1:3306 / rdcdb）。

### 8.3 参数解析 `lib/query.ts`

- `parseIntParam(value, default, {min, max})`：非法/越界回退默认值
- `parseBooleanParam`：多写法布尔解析
- `parseExpandParam`：逗号分隔 → `Set<string>`

### 8.4 统一错误响应 `lib/http.ts`

`errorResponse` / `validationError`(422) / `notFound`(404) / `serverError`(500) 四个构造器，保证全 API 错误格式一致。API 路由统一用 try/catch 包裹，未知异常降级为 500。

## 9. 数据流水线（CSV → MySQL）

### 9.1 流程总览

```text
标准化 CSV（csv_templates_normalized/*.csv，每表一个文件）
        │
        ▼
① validate_csv_data.py（Python，只读校验）
   对照 main.sql 校验表结构、字段、类型、枚举、外键引用
   输出报告 → csv_validation_reports/
        │
        ▼
② upsert_table_from_csv.js（Node，diff/写入）
   dry-run：打印差异摘要（默认）
   --apply：写入数据库（默认先自动建备份表）
        │
        ▼
③ GitHub Actions 手动触发 或 本地执行
```

### 9.2 校验脚本 `validate_csv_data.py`

- 仅用 Python 标准库，读取 `main.sql` 解析表结构，逐表校验 `csv_templates_normalized/` 下 CSV
- 支持表头别名映射（如 `Type → biodist_type`），忽略系统列（`id/created_at/updated_at`）
- 校验内容：必填列、类型（数值/日期/枚举）、外键引用完整性（按 `TABLE_ORDER` 依赖顺序）
- 输出 Markdown/JSON 校验报告，CI 中作为 Artifact 上传

### 9.3 入库脚本 `scripts/upsert_table_from_csv.js`

```bash
npm run upsert:csv -- --table <表名> --csv <路径> [选项]
  --key <列1,列2>          # 业务主键（联合键）
  --apply                  # 实际写入（默认 dry-run）
  --replace-table          # 整表替换（配合 --apply）
  --compare-all-columns    # 无稳定主键表的全列比对（只读）
  --no-backup              # 跳过自动备份表
  --schema / --env         # 自定义 schema 与环境文件路径
```

- 自动解析 `main.sql` 获取列定义与唯一键；`--key` 未指定时取第一个单列唯一键
- `--apply` 前自动创建 `<table>_backup_<日期>` 备份表（可用 `--no-backup` 跳过）
- 写入策略：按业务键 upsert（存在则比对更新，不存在则插入）

### 9.4 表与主键映射（CI 内置）

| 表 | 业务主键 | 特殊策略 |
| --- | --- | --- |
| rdc_drug | drug_id | - |
| target / indication / reference / chemical_affinity / human_activity / animal_in_vivo_study | 各自 *_id | - |
| drug_target / drug_indication / rdc_drug_reference | 二列联合键 | - |
| chemical_entity | entity_category,entity_id | - |
| drug_chemical_rel | drug_id,relation_role,chemical_entity_id | - |
| in_vitro_measurement / animal_in_vivo_biodist / animal_in_vivo_efficacy | 无 | `--replace-table` 整表替换 |

### 9.5 本地全量导入

`./run_upserts.sh`：按依赖顺序对全部 16 张表执行 `--replace-table --apply`，用于初始化数据库。

## 10. 部署与运维

### 10.1 部署拓扑

- **服务器**：阿里云 ECS
- **进程**：PM2 fork 模式，应用名 `rdc-api`，`next start -p 3101`，最大内存 500M 自动重启，日志写入 `logs/`
- **入口**：Nginx 443 → 127.0.0.1:3101
- **域名**：rdcdb.com

### 10.2 CI/CD（GitHub Actions）

两条工作流均为 **手动触发（workflow_dispatch）+ production 环境保护**：

#### `deploy-code.yml`（代码部署）

1. 输入分支名 + 确认串 `DEPLOY_TO_PRODUCTION`（防误触发）
2. 通过 `DEPLOY_SSH_KEY` 等 Secrets 建立 SSH 连接
3. 远程执行：`git pull --ff-only` → `npm ci` → `npm run build` → `pm2 restart` → `pm2 save`
4. 并发组 `production-code-deploy` 串行化部署

#### `database-csv-patch.yml`（数据补丁）

1. 选择目标表 / CSV 路径 / 模式（dry-run 默认，apply 需确认串 `APPLY_TO_PRODUCTION`）
2. `npm ci` → Python 3.12 环境准备
3. 全量 CSV 校验（validate_csv_data.py）并上传校验报告 Artifact
4. `node --check` 语法检查 → 对全部表 dry-run diff
5. apply 模式才执行目标表写入（ Secrets 注入 DB 连接，直连生产库）

### 10.3 日常运维操作

| 操作 | 方式 |
| --- | --- |
| 发代码 | GitHub → Actions → Deploy Code → 填分支 + `DEPLOY_TO_PRODUCTION` |
| 更数据 | GitHub → Actions → Database CSV Patch → 先 dry-run 看报告，再 apply |
| 看日志 | 服务器 `pm2 logs rdc-api`，或 `logs/` 目录 |
| 重启 | `pm2 restart rdc-api` |
| 建库 | `mysql < main.sql`（幂等，`CREATE TABLE IF NOT EXISTS`） |
| 导数据 | `./run_upserts.sh`（本地全量） |

## 13. 错误处理与规范

1. **API 错误**：统一 `{error: {code, message, details}}` 结构（见第 6.1 节）
2. **排序白名单**：`/api/rdc` 的 sort 参数仅允许 4 个枚举值，杜绝 ORDER BY 注入；SQL 一律参数化查询（`?` 占位符）
3. **分页钳制**：`page_size` 限制 1–100，防止大结果集拖垮内存
4. **外部调用超时**：IP 归属地查询 3 秒超时（AbortController），失败不阻塞埋点主流程
5. **表缺失容错**：数据表不存在时 API 返回空数据而非 500
6. **生产变更保护**：部署/数据写入均需手动输入确认串（`DEPLOY_TO_PRODUCTION` / `APPLY_TO_PRODUCTION`），数据写入前自动备份
